perf(acquisition): 修复采集帧率崩塌 - 模型推理按时间节流, 7.36→13.58fps

【问题】采集帧率中位仅7.49fps, 间隔分布呈双峰: 主峰约7.5fps, 另有一个
尖锐次峰精确落在 2.000s(占大间隔的93.6%, std极小, 且完全没有1.0s档
=> 排除浏览器后台节流)。11.6%的帧间隔>1.3s。

【定位过程】
1. 排除前端上传: 直接压测 /upload_frame, 实测可承受31fps(中位20ms),
   后端接收完全不是瓶颈。
2. 排除人脸丢失: [FACE-DIAG]统计人脸连续丢失中位仅2帧、共243次事件,
   远不足以解释23008次2秒停顿。
3. 逐环节实测耗时(单线程 rppg_processing_loop 内串行):
       MTCNN人脸检测(640x480)  :   12.5 ms
       PhaseNet推理(160帧序列)  : 1167.0 ms   <-- 占99%
   缓冲区攒满160帧后, 每收到一帧新画面就跑一次1167ms全序列推理,
   线程被彻底占满 => 理论上限0.8fps。
4. 对照验证假设: 首个窗口(缓冲填充期, 尚未推理) >1.3s停顿占比 0.0%;
   后续窗口(缓冲已满, 每帧推理)                 >1.3s停顿占比 11.6%。
   2秒档占比 0.0% -> 10.5%。假设成立。

【修复】新增 MODEL_INFER_MIN_INTERVAL_SEC = 2.0, 按真实时间节流推理。
关键: 只节流"多久算一次心率", 不节流"多久采一帧"——帧仍然照常入缓冲区。
心率窗口本身长10秒, 0.5次/秒的刷新完全足够。

【为什么帧率重要】用真实采集帧做降采样对照, 帧率越高结果越稳:
    ~3.7fps: 会话间std 2.69 | ~7.5fps: 1.73 | ~15fps: 1.12 (单调改善)

【线上实测效果】(节流前200窗口 vs 节流后25窗口)
    采集帧率      7.36 -> 13.58 fps  (1.85倍, 与理论预测13fps吻合)
    >1.3s停顿    12.1% -> 0.2%
    2秒档停顿    11.1% -> 0.0%      (尖峰完全消失, 证实根因)
    160帧覆盖时长 23.9s -> 13.3s     (越接近窗口10秒, 时间尺度越真实)

【附带收益】推理频次从约4.2次/秒降到0.5次/秒, 同时降低了"高更新密度"
对追踪逻辑的放大效应(见 compute_hr_spectral_centroid 注释块)。

【锁定区完整性】两处锁定区块均逐字符零差异。
MODEL_INFER_MIN_INTERVAL_SEC=0 可完全关闭节流、恢复原每帧推理行为。
